# Next 16: why, and the two things that are not obvious

Upgraded 2026-08-05, from `next@15.5.20` to `16.3.0`, with
`payload@3.87.0` and `@opennextjs/cloudflare@1.20.2`.

## Why: the previous combination was unsupported

`@payloadcms/next` declares

```
>=15.2.9 <15.3.0 || >=15.3.9 <15.4.0 || >=15.4.11 <15.5.0 || >=16.2.2 <17.0.0
```

**Nothing between 15.5.0 and 16.2.2.** The project ran 15.5.20, which
satisfies none of it — and the whole admin panel and every `/api/*` route
go through that package. There was no patch-level escape either: no 15.5.x
release is supported, so Next 16 was the only way back into a combination
where all four dependencies agree.

`@opennextjs/cloudflare` 1.20.2 had also raised its 15.x floor to
`>=15.5.21`, so it could not be updated without moving Next anyway.

This went unnoticed for weeks while the dev server misbehaved and the
symptoms were worked around in tests. Check peer ranges before writing the
second workaround.

## Dev uses Turbopack. The production build does not.

`package.json`'s `build` script passes `--webpack`, deliberately.

Turbopack is the Next 16 default and is a large win in development — the
dev server is ready in ~340ms rather than seconds. But it rewrites module
specifiers, and `@payloadcms/drizzle` reaches drizzle-kit through
`createRequire` + `require('drizzle-kit/api')`. Turbopack turns that into
an internal hashed name, and OpenNext's esbuild pass then fails:

```
ERROR: Could not resolve "drizzle-kit-8c53b399dac79e94/api"
```

on five chunks. `serverExternalPackages: ["drizzle-kit"]` does **not**
prevent the rewrite — that was tried.

Nothing needs drizzle-kit at runtime: it exists for drizzle's schema push,
and this adapter runs with `push: false` because push recreates indexes D1
already has. So the fix is to keep Turbopack away from it, using the
`--webpack` opt-out Next 16 documents.

`next.config.ts` therefore configures both builders, and that is not
redundancy. Turbopack resolves TypeScript extensions itself; webpack needs
the `resolve.extensionAlias` mapping `.js` to `.ts`, because Payload and
Lexical ship ESM whose relative imports carry a `.js` extension that only
exists as `.ts` on disk.

Revisit when [opennextjs-cloudflare#569](https://github.com/opennextjs/opennextjs-cloudflare/issues/569)
lands more of the Turbopack path. `next dev` is unaffected either way.

## What else changed

- **`eslint` config option removed** from `next.config.ts` — Next 16 deletes
  it along with `next lint`. Linting was already a separate `eslint` script;
  `ignoreDuringBuilds` simply has nowhere to live now.
- **`AGENTS.md` and `CLAUDE.md` are generated by `next dev`** and committed.
  Not committing them means every dev run dirties the tree. Disable with
  `agentRules: false` in `next.config.ts` if that is not wanted.
- **`tsconfig.json`** was rewritten by `next dev`: `jsx` is now `react-jsx`
  (mandatory) and `.next/dev/types/**/*.ts` was added to `include`. The rest
  of that diff is reformatting.
- **`next dev` and `next build` now use separate output directories**
  (`.next/dev`), so they can run at the same time. `/.next/` in `.gitignore`
  already covers it.

## Checked and found not to apply

Async request APIs (already awaited everywhere), `revalidateTag`'s new
required argument (only `revalidatePath` is used), `middleware` → `proxy`
(no middleware), parallel-route `default.js` (no slots),
`serverRuntimeConfig` (unused), `images.domains` (already `remotePatterns`),
`images.imageSizes` dropping 16 (set explicitly), PPR flags (unused).
